# 前端目录结构（拆分说明）

> 面向改前端的人。**前端没有构建步骤、没有框架、没有打包器** —— 这一条从拆分前到现在都没变，
> 拆分方式就是为了保住它。

## 1. 为什么拆

原前端是**一个** `src/index.html`（15874 行：1 块内联 `<style>` + 1 块内联 `<script>`）。
十几万行字符挤在一个文件里，改任何一处都要在 1.5 万行里滚，diff 也永远只显示"某一行变了"，
看不出改的是哪个功能。

现在拆成 **4 个 CSS + 15 个 JS + 272 行骨架**，按功能分文件。**拆的是文件，不是架构**：
所有代码仍在同一个全局作用域里，行内 `onclick` 与既有函数互相调用照旧。
（15 个 JS 里 **1 个是生成文件** `81-ble-uuids.js`，见第 7 节。）

## 3. 三条硬规矩（拆分的全部意义就在这三条）

1. **只用普通 `<script src>`，绝不用 `type="module"`。**
   模块有独立作用域，所有行内 `onclick`（拆分时 51 处 HTML + 151 处动态拼接的模板串）会立刻失效，
   而且会退化成"点了没反应"这种最难查的故障。同理 CSS 用 `<link>` 而不是 `@import`。
2. **顺序不能乱调，而且"顶层代码"只能依赖本文件/更早文件里的东西。**
   这条比看起来严格：在**同一个** `<script>` 里，`function f(){}` 是**提升**的 —— 顶层代码写在文件开头也能调用文件末尾声明的函数；
   拆成 14 个脚本之后，提升**不再跨文件**，同样的调用会变成 `ReferenceError`。
   CSS 同理：层叠靠顺序（主题变量必须最先加载）。
   ⚠️ **被 `try { … } catch` 包住的初始化代码最阴**：ReferenceError 会被吞掉，应用照常启动，
   只是那块初始化悄悄不生效（主题没应用、监听没注册）。**别把初始化代码包进 try/catch**，除非你确定失败可以忍受。
   拆分时专门扫过一遍（一次性脚本，已删除）：14 个文件的**列首可执行语句**只有 3 处 ——
   `00-bootstrap.js` 的 `new TextDecoder()`、`70-config.js` 的 `applyTheme(getSystemTheme()) / syncThemeUI()`（它们都定义在**同一个文件的上方**）
   与两处 `setTimeout(...)` 回调（在所有脚本加载完之后才跑）。顶层字面量里唯一"引用了更晚文件"的是
   `30-mcp.js` 的 `MCP_SERIAL_FUNCS.clear`，但那是个**函数值**（调用发生在运行时，不是初始化期）。
   要加新的顶层调用，先确认被调函数在**本文件之前**已经声明。
3. **不引入构建步骤。** 没有打包、没有转译、没有 minify：`frontendDist` 就是 `../src`，
   Tauri 把整个目录原样打进 exe。加一个构建器就意味着"运行的不是仓库里那份代码"。
   ⚠️ 同理**加新文件不用注册到任何清单**：`src/index.html` 的标签列表就是唯一的清单 ——
   编号插在语义相邻的位置（`55-`、`84-` 这样），同时把标签写进 `index.html`。

## 4. 断言集怎么看这些文件

`.walkthrough/gen_ble_preview.js` 里几百条断言有大量**跨 CSS/JS 的源码正则**
（例如"`.qcmd-goto` 这个类有没有定义""后端发的每个 `op` 前端有没有对应分支"）。
它们的本意是"这段内容在前端里"，而不是"它写在内联标签里"。

所以断言集不去读单个文件，而是走 `readFrontendSource()`：读 `src/index.html` 骨架，
再**按标签顺序**把 `css/*.css`、`js/*.js` 内联回去（`<style>…</style>` / `<script>…</script>`），
拼成一个"逻辑单文件"。顺序不变 ⇒ 正则行为与拆分前完全一致 ⇒ **拆分时一条断言都没改**。
`vendor/xterm/*` 不内联（它本就是外部文件）。加新前端文件**不用改断言集**，只要标签写进 `index.html`。

## 5. 新代码放哪一块

| 你要加的东西 | 放哪 |
|---|---|
| 某个面板的样式 | 对应面板的 css（新面板就新建一块，编号插在相近位置） |
| 某个面板的行为 | 对应面板的 js |
| 跨面板的纯工具函数 | `40-utils.js` |
| 启动 / 初始化 / 窗口控制 | `00-bootstrap.js`（早）或 `90-init.js`（晚，DOM 之后） |
| 给 AI 用的语义层（MCP） | `30-mcp.js` |
| 两处都要用的常量 | 放在**第一个**用到它的文件之前（普通脚本没有 hoisting 跨文件） |
| 从官方数据生成的大表（如 BLE UUID 名称表） | 生成文件 + 生成器；见第 7 节 |

拆分是**纯搬家**，用一个一次性脚本 `.walkthrough/_verify_split.js` 逐字符验证过，10 条全过：

- 4 个 css 去掉文件头注释后拼回去 == 原 `index.html` 第 8-2460 行（125479 字符，逐字相等）
- 14 个 js 去掉文件头注释后拼回去 == 原 `index.html` 第 2706-15870 行（613892 字符，逐字相等）
- body 骨架 2465-2704 行逐字保留；`<script src>` / `<link>` 顺序 == 切分顺序
- 没有 `type="module"`；`vendor/xterm/*` 引用原样保留；所有新文件行尾与原文件一致（CRLF）

断言集 `.walkthrough/gen_ble_preview.js` 拆分前后均为 **1730 passed / 0 failed**（未改任何断言）。
校验脚本与备份文件在校验通过后已删除 —— 上面的数字就是证据，重建方式见 §3（拼回去即成原文件）。

## 7. 生成文件：BLE 的 UUID 名称表（`81-ble-uuids.js`）

**它是什么**：服务名 / 特征名两张表（`BLE_SVC_NAMES` / `BLE_CHAR_NAMES`），
内容是"UUID ↔ 官方名称"这个**事实**。以前这两张表手写在 `81-ble.js` 里，特征只有 **9 条** ——
而 SIG 公报的特征有 **512 条**：既不全，也没法跟进更新（用户的追问："这个表足够完整吗？"）。

**怎么生成**：

```bash
node .walkthrough/gen_ble_uuids.js            # 联网抓 SIG 官方数据 → 重写 81-ble-uuids.js
node .walkthrough/gen_ble_uuids.js --from <目录>   # 离线：读目录里存好的两个 yaml
node .walkthrough/gen_ble_uuids.js --check     # 只比对，看有没有更新（不写文件）
```

数据源是 Bluetooth SIG 官方公开仓库的 `assigned_numbers/uuids/{service,characteristic}_uuids.yaml`
（<https://bitbucket.org/bluetooth-SIG/public/src/HEAD/assigned_numbers/uuids/>）。
生成物头部会写清**抓取日期与提交号**，所以"这份表是什么时候的快照"永远查得到。

**为什么源文件不进仓库**：那份 YAML 的抬头写明 *"This document is proprietary to Bluetooth SIG …
The furnishing of this document does not grant any license"* —— 不能随产品再分发。
所以只有**生成物**（我们自己的 JS 表）进仓库，生成是开发者本地跑一条命令的事。
（对比过 Nordic 的 BSD-3 镜像 `bluetooth-numbers-database`：它可再分发，但只是个镜像 ——
实测比 SIG 少 8 个服务、60 条特征，还留着 23 条已废止的旧编号，拿它当源反而更差。）

**三条纪律**：

1. **别手改生成物**：改了会被下次生成覆盖，而且 `--check` 会报"与 SIG 不一致"。
   要加 SIG 表里没有的条目，加进生成器的 `SVC_EXTRA`（带出处），不要改产物。
2. **生成物必须一起提交**：前端没有构建步骤，跑起来直接加载这个文件；不提交 = 名字全没了。
3. **兜底逻辑不在这个文件里**：查不到服务 → `renderBleServiceRow` 里统一标 `Custom Service`
   （2026-09 用户明确要求保持不动）；查不到特征 → 不显示名字。加条目**不要**去动那条兜底。
