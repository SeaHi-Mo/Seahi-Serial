This release fixes two problems in quick command looping and adds a troubleshooting skill for "access denied" failures during Windows builds.

### 🐞 Fixed

**1. A command without an expectation was sent only once**

- Symptom: a command with no expectation column (for example `| 1 | 121351564 | 3000 | false |  | 3 |  |  |`) was sent once and then the loop stopped and the switch turned off, which looked like "commands without an expectation can only be sent once".
- Root cause: an empty expectation still fell back to the built-in `OK` judgement. A device that never replies `OK` therefore timed out, which terminated the whole chain.
- Now the expectation column is also the switch for "does this command wait for a reply": empty means no reply is checked and the next command follows; to wait for the built-in `OK`, write `OK` explicitly. It is still an additional success word, so `OK|WIFI GOT IP` accepts both.

**2. The meaning of the timeout cell is settled: it is the time this command occupies**

- With an expectation it is the upper bound for waiting: the chain moves on as soon as the reply arrives, and at the limit it follows the failure jump, or terminates when none is configured.
- Without an expectation it is the interval before the next command, so `3000` means one command every three seconds.
- `0` falls back to the 20 ms minimum gap, which prevents a tight loop from flooding the port.

**3. Looping no longer produces any messages**

- The output lines such as "command N sent (no expectation, next in 3000 ms)" and the summary printed when the loop starts were removed: sending happens silently, and whether the loop is running is visible from the switch in the panel, or the small dot on the collapsed bar.
- Commands that wait for a reply still log each step (sent, OK received, retry n of N, termination reason), and self-healing stops (disconnect, nothing left to send, jump loop) still explain themselves, because those are errors rather than routine traffic.
- Whether a command waits for a reply is shown by hovering the timeout cell.

**4. Stopping and immediately restarting the loop fired an extra tick**

- The old tick was still sleeping in its interval; when it woke up it deleted the new round's re-entry guard and could even send a command or perform a jump on behalf of the new round. Every round now has its own id, and a tick that wakes up in the wrong round is discarded.

### 📄 Documentation

- The new looping rules are reflected in `doc/QUICK_CMDS.md`, `README.md`, `doc/ARCHITECTURE.md` §6.4.1, and in the `serial_quick_cmd` tool description with its `timeoutMs` and `expect` fields.
- New `skills/win-build-access-denied`: how to diagnose and fix "access denied / OS error 5" during a Windows build that prevents `npm run dev` from opening a window.
