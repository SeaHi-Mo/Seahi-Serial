This release adds the Streamable HTTP transport that newer AI clients require, letting users choose which transport to serve, and connects WSL serial ports to MCP while fixing a series of problems behind it. The most important one: on distributions without `sg`, WSL serial ports could not be opened at all (issue #21).

### ✨ New

**Streamable HTTP transport (`POST /mcp`) with three modes**

- Newer clients such as VS Code, Cline, recent Cursor and Claude Code use Streamable HTTP by default, while older clients still speak SSE, so both are kept and share the same tools, session table and limits.
- The two switches in the dialog became one dropdown: `HTTP`, `SSE` or `All` (default). With a single mode selected, the other endpoint returns 404 immediately, without a restart.
- The client configuration dialog and `npx seahi-serial-mcp` both show the `http` and `streamableHttp` spellings, because clients disagree; the wrong spelling is parsed silently as legacy SSE and ends in an unexplained "cannot connect".

**WSL serial ports over MCP**

- New `ui_get_state{section:"wslDevices"}` exposes the WSL port mapping table (`busid`, Windows COM name, name, status, `wslPath` and the control path for `ui_set`).
- `serial_*` with `pane:"wsl"` now addresses the WSL pane, and `serial_get_state` gains `portOptions`: which ports that pane can select, `COM3` on Windows and `/dev/ttyUSB0` on WSL.

### 🐛 Fixed

- **WSL serial ports failed on distributions without `sg`** (issue #21). The bridge hard-coded `wsl -d <distro> -e sg dialout -c "python3 …"`, and `sg` comes from the shadow package, which minimal images such as Alpine often lack, so the relay failed with `execvpe(sg) failed`. `sg` is now used only when switching groups non-interactively is confirmed to work, and the hint "this distribution lacks `sg`, install shadow" was added. The same line had a second failure mode: when `sg` exists but the user is not in `dialout`, it prompts for a password, and its stdin is the JSON pipe, which looked like a start timeout with no explanation.
- **Serial tools were blocked for the WSL pane** because `serial_open{pane:"wsl"}` checked the number of Windows COM ports, and after `usbipd bind` into WSL the port no longer exists on the Windows side. The check is now per pane: Windows checks COM ports, WSL does not.
- **Mapping a device reported false success**: the checkbox replied synchronously while the real action goes through `usbipd`, which can take tens of seconds and may prompt for elevation. The reply now carries `mapRequest.settled=false` with an explanation, so AI no longer assumes the mapping is done.
- **Devices could be mis-addressed, and the wrong device mapped**: rows had no ids, so AI saw fallback names such as `input_127`, and addressing was by index while the table is redrawn every five seconds. Rows, mapping and auto-mapping now have stable ids carrying the device identity, mapping is addressed by busid, and the registry rebuilds when elements are replaced by `innerHTML`.
- **The interface did not switch panes when AI acted**: write actions bring the pane to the front, as BLE and ADB already did, while read-only actions switch nothing. WSL panes are created lazily, so a write creates the pane and a read tells the user to open it.
- The `serial_select_port` description claimed values must come from `serial_list_ports`, which is wrong for WSL panes where values are paths such as `/dev/ttyUSB0`.

### 📚 Documentation and tests

- `doc/MCP.md` gains a four-step walkthrough for mapping a USB serial port into WSL, and `doc/ARCHITECTURE.md` §5.8 records the three "do not revert" rules for starting the bridge.
- The tool count stays at 55: the WSL work deliberately reuses `serial_*` with `pane` instead of adding a parallel tool set.
- Backend tests went from 188 to 216 and frontend assertions from 1494 to 1651, including one that compiles every inline `<script>` in `index.html` as a whole to catch syntax errors in functions the per-function assertions never reach.
